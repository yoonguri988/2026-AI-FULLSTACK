TRANSACTION

부서를 지운다는 건, 함께 옮긴다는 것

왜? 부서를 삭제하려면 소속 사원을 전부 다른 부서로 옮겨야 하는데, 예약·결재 등 여러 모듈이 부서가 아닌 사원(emp_id)을 참조하고 있어 관리자가 전체 영향 범위를 한눈에 파악하기 어려웠습니다.

됐다! 이관 대상을 사원 단위로 좁히고 여러 사원의 이관을 하나의 트랜잭션(@Transactional)으로 묶어 하나라도 실패하면 전체 롤백되도록 설계했습니다. 부서 상태를 ACTIVE→PENDING_DELETE→DELETED 3단계로 관리해, 사원 전원 이관이 끝나면 부서가 자동으로 소프트 삭제되도록 만들었습니다.

PAYROLL · DI

계산기를 나눴더니, 누가 먼저?

왜? 장기요양보험료·지방소득세처럼 일부 항목이 다른 항목의 계산 결과에 의존하는데, 급여 계산기(Strategy 패턴) 10종을 Spring List로 주입하다 보니 주입 순서만으로는 실행 순서를 보장할 수 없었습니다.

됐다! 오케스트레이터가 주입 순서에 기대지 않도록 바꾸고, 의존하는 계산기(장기요양보험·지방소득세)가 필요한 선행 계산기(건강보험·소득세)를 Spring DI로 직접 주입받아 자기 내부에서 호출하는 구조로 재설계했습니다.
